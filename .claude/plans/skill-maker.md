# skill-maker 제작 계획

> 계획 세션에서 승인됨. 파일명은 계획 세션 종료 직후 `.claude/plans/skill-maker.md`로 변경 완료.

## Context

성진은 하네스 제작 스킬 `harness-creator`와 범용 계획 인터뷰 스킬 `interview`를 이미 만들었다. 이번에는 스킬 제작에 특화된 메타 스킬 `skill-maker`를 이 레포(`.claude/skills/skill-maker/`, 현재 빈 `SKILL.md`와 빈 `scripts/`)에 만든다. 목표는 Claude의 지능과 창의성을 해치지 않으면서, 사용자의 도메인 지식과 판단을 Claude가 체화해 전문가처럼 유연하게 일하게 하는 스킬을 만드는 것이다. 성공 기준은 오직 품질이다.

**한 문장 목표:** 사용자의 암묵지를 기본값 대조 인터뷰로 끌어내 원칙·인터페이스·완료 기준으로 증류한 스킬을 만들고 고치는, 수동 호출 전용 단일 파일 메타 스킬을 만든다.

비판적 전제 (근거와 함께 합의됨):
- 어려운 지점은 스킬 문서 형식이 아니라 지식 추출이다. 전문가는 암묵지를 질문만으로는 다 말하지 못하고, 구체적 산출물을 보면 즉시 판정한다.
- harness-creator는 Claude Code 메커니즘 비중이 크고 그 사실을 참으로 유지하는 부채가 컸다 (사실: 문서 대부분이 훅·스킬 메커니즘, 커밋 이력의 사실 오류 수정 #49·#55~#60). skill-maker는 판단 지식 중심으로 가고, 메커니즘은 프로브로 거른 최소만 담는다.
- 원샷 e2e는 수백 번의 실사용 품질을 증명하지 못한다. 행동 검증은 실사용과 개선에 맡긴다.
- codex 독립 감사(L3, gpt-6-astra medium)의 결론: harness-creator는 판단 약 42% 대 메커니즘 약 58%다. 적힌 이유보다 강한 명령, 편집자 메모, 클라이언트 소유 수치가 남아 있다. 가장 큰 빈틈은 "사용자 사례에서 판단 지식을 어떻게 찾는가"다. 그래서 skill-maker의 중심은 **사례 → 구별 기준 → 이유 → 반례 → 재사용 가능한 지침**이다. 계승할 것은 "이 줄을 지우면 틀리는가" 검사와, 추가할 지식이 없으면 만들지 않는 판단이다.

## 평가 기준 — 네 프레임

"사용자"는 스킬을 실행하는 모델이다 (근거: harness-creator 커밋 345f7e3). skill-maker 자체와 skill-maker가 생성하는 스킬 모두에 이중 적용한다.

- **principle over rail** — 행동을 막는 레일 대신 그 행동을 결정하는 이유와 대상의 실제 구조. 고정 순서·절대 금지는 다른 길을 못 고르는 이유가 되는 실패가 있을 때만.
- **interface over document** — 도구가 소유하는 계약은 산문 복제 대신 인터페이스(help·choices·스키마·오류 메시지·frontmatter)에. 출력도 설계 대상(P2).
- **for user not developer** — 런타임 문서엔 실행 모델의 행동을 바꾸는 것만. 참조 문서 출처, 발견 경위, 결정 이력, 인터뷰 기록 같은 유지보수 메모는 커밋·PR로. 판별: "모델이 이 줄로 행동하는가, 이 줄의 출처를 기록할 뿐인가". 실행 중 모델이 실제로 여는 URL은 인터페이스라 남는다. 측정·사례 서술은 다음 실행의 판단을 바꿀 때만 남는다.
- **dense information** — 재도출 가능하게 하는 이유는 남기고 재진술·방어 논증·계산 가능한 결과·모델이 이미 아는 것은 제거. 클라이언트 소유 값은 숫자 대신 실패 형태로. 필요한 예시·예외는 분량을 이유로 자르지 않는다.

**가정**
- A1: `claude plugin validate`는 깨진 YAML frontmatter도 잡는다. 구현 1단계에서 실측. 틀리면 조용한 메커니즘 섹션에 "YAML 깨짐은 validate로 안 잡힌다"를 싣고 frontmatter를 직접 파싱해 확인하게 한다.
- A2: 한 skill-maker 세션 안에서는 컴팩션이 일어나지 않는다 (성진 결정: 1M 컨텍스트). 실제로 컴팩션이 일어나면 재개.

**기각·보류한 후보** (재개 조건과 함께)
- 기본값 실행 래퍼 스크립트: `claude -p` 플래그 변화나 격리 실수가 실사용에서 반복되면 재개.
- 자체 lint: `claude plugin validate`가 못 잡는 조용한 실패가 실사용에서 나오면 재개.
- 생성 스킬 with-skill 재실행: 실사용 개선 루프로 부족하다는 증거가 쌓이면 재개.
- harness-creator 분담 재조정(HC 수정): 이번 범위 밖.

## SKILL.md 섹션 구조 (영어로 작성, 하드랩 없음)

```yaml
---
name: skill-maker
description: <한 줄: 사용자의 전문성을 인터뷰로 끌어내 스킬을 만들거나 고친다>
disable-model-invocation: true
---
```

1. **`# Turning a user's expertise into a skill`** (도입)
   - 스킬이 하는 일: 모델의 기본값과 전문가 판단의 차이를 이유와 함께 옮겨, 적히지 않은 경우에도 전문가처럼 판단하게 한다. 이미 잘하는 것에는 손대지 않는다(지능·창의성 보존).
   - 권한 분담: 사용자는 지식·가치·목표의 주인, 실행 모델은 그것을 작동하는 스킬로 만드는 쪽. 따라서 솔직한 반대가 의무다.
   - 새 스킬이든 기존 스킬이든 같은 이해를 적용한다. 출발점만 다르다(D6).
2. **`## What earns a place in a skill`** (좋은 스킬의 기준)
   - 네 프레임을 생성 스킬의 판정 기준으로. 각 프레임에 재도출 가능한 이유 한 절.
   - 모델이 이미 아는 것은 담지 않는다. 판정은 추측이 아니라 기본값 대조로.
   - 개발자 메모 판별 기준과 경계 사례(출처 메모 vs 실행 중 여는 URL).
   - 기본값을 교정하는 문장: 피할 행동과 그 이유는 본문에 둔다. 어떤 모델·조건에서 관찰했고 언제 재검토할지는 개발 기록에 둔다. 모델이 바뀌면 그런 문장을 다시 연다.
   - 추가할 지식이 없으면 스킬을 만들지 않는 것도 정답이다(D20).
3. **`## Drawing out what the user knows`** (추출)
   - 추출 대상: 신념 목록이 아니라 무엇을 보고(단서), 무엇을 구별하며, 언제 판단을 뒤집는가(반전 조건). 원칙끼리 충돌할 때의 우선순위 조건도 포함.
   - 증거 먼저: 사용자의 산출물·문서·세션 전사·기존 스킬·실패 사례. 읽을 수 있는 것을 사용자에게 묻지 않는다.
   - 기본값 대조: 대표 과제를 임시 디렉터리에서 `claude -p --safe-mode --model <대상 모델>`로 수행 → 사용자 비판 → '왜'를 파서 원칙화. 과제에 필요한 사실·자료는 넘기고 시험할 판단 지침은 뺀다. 자료·도구가 없어 못 한 결과는 전문성 차이가 아니다(D9). 호출 형태는 사전 승인 패턴과 일치해야 한다(D16). 1단계 프로브에서 확인한 실행상 실패 형태만 싣는다.
   - 권위 구분: 개인 선호, 확인 가능한 사실, 조직 관행, 어길 수 없는 제약을 같은 무게로 쓰지 않는다. 사실 주장은 증거와 대조하고, 강제 조건에는 이유를 요구한다. 결과를 안 뒤의 설명과 당시의 판단을 구분한다.
   - 탐침: 구체 산출물 비교, 초보자가 틀리는 지점, 반례, 뒤집은 가정. 추상 질문("무엇이 중요한가요?")보다 효과적.
   - 답 주입 경계: Claude가 다듬은 원칙에 대한 동의는 약한 증거다. 판단이 갈리거나 경계가 애매한 원칙은 추출에 쓰지 않은 사례나 조건 하나를 바꾼 사례에 적용해 보이고 판정을 받는다(D19).
   - 합의: 결과를 바꿀 수 있는데 증거로 못 정하는 것은 AskUserQuestion으로, 한 번에 하나의 결정, 추천안 먼저. 확인할 필요 없는 사실은 출처와 함께 말하고 넘어간다. 사실·추론·결정·가정·미결을 구분하는 장부.
   - 저장 위치와 본문 언어는 사용자와 정한다(P3).
   - 기존 스킬에서 출발할 때: 스킬 본문은 앞선 결정의 증거, 실패 보고는 원인을 추적할 증거. 지식이 빠진 것인지 실행이 실패한 것인지(자료·도구 부족, 상위 지시 충돌, 모델 한계) 먼저 가른다. 한 번의 교정인지, 반복되는 선호인지, 기존 원칙의 반례인지 가른다. 보존할 행동을 먼저 알고 나서 가장 작은 원인 범위를 고친다. 삭제와 통합도 개선이다.
4. **`## Writing judgment down`** (증류)
   - 원칙 + 이유 + 성립 조건과 뒤집는 조건 + 판단이 갈리는 구체 사례. 표어("맥락에 맞게")는 상반된 행동을 모두 정당화하므로 원칙이 아니다. 레일은 다른 길을 못 고르는 이유가 되는 실패가 있을 때만 쓰고, 이유가 요구하는 범위보다 강하게 쓰지 않는다.
   - 예시는 탐색 공간을 좁힌다. 정답 템플릿이 아니라 비슷한 두 사례에서 판단이 갈리는 이유를 보여주는 데 쓴다.
   - 모델 기본값과 싸울 때는 막연한 지시 대신 피할 패턴을 구체적으로 이름 붙인다.
   - 완료 기준: 생성 스킬이 다루는 작업이 언제 끝났는지 판정 가능하게 적는다. 반드시 보존할 속성과 자유롭게 바꿔도 되는 부분을 구분해 창의성을 막지 않는다.
   - 인터페이스: 루브릭·템플릿·스키마·CLI. CLI라면 입력은 self-describing help, 출력은 요약 먼저 + 원문 손잡이(P2). 맥락에 따라 달라지는 판단은 고정 분기로 바꾸지 않고, 확정된 계산·검증 계약은 인터페이스로 옮긴다.
   - 로드 시점으로 파일 분리, 분기 지점에 조건 달린 포인터(P1). 패키지될 스킬은 자기완결.
   - description: 트리거는 description만 본다. 드러난 키워드가 아니라 의도로 쓰고, 이웃 스킬과의 near-miss 경계까지 적는다.
5. **`## Mechanics that fail silently`** — 1단계 프로브를 통과한 항목이 있을 때만 두고, 각 항목을 한 문단의 실패 형태로 쓴다(D15). 통과한 항목이 없으면 섹션을 만들지 않는다.
6. **`## When the skill is done`**
   - 사용자가 스킬 전문을 승인했다. 부분 승인이나 침묵은 승인이 아니다. 또는 추가할 지식이 없다는 근거에 사용자가 동의해 만들지 않고 끝냈다(D20).
   - 핵심 판단과 경계가 설명됐고, 큰 원칙 충돌이 해결됐으며, 남은 불확실성이 드러나 있다. 문서 승인은 실사용 품질의 증명이 아니므로 그렇게 주장하지 않는다.
   - `claude plugin validate --strict`가 실경로에서 통과한다. 심링크는 따라가지 않는다.
   - 기본값 대조에서 나온 차이마다 스킬 안에 담긴 자리가 있거나 뺀 이유가 기록돼 있다.
   - 실행 코드를 만들거나 바꿨다면 그 입출력·실패 계약을 코드의 검증 방법으로 확인했다(D21).
   - 보이기 전에 독립 검토를 거쳤거나, 거치지 못한 사실과 남은 위험을 밝혔다(D17).
   - 출처·인터뷰 기록·기각 사유 같은 개발 기록은 스킬 밖(커밋 본문이나 사용자에게 돌려주는 핸드오프)에 둔다. 저장 위치가 정해져 있지 않으면 새 기록 파일을 만들기 전에 사용자와 정한다.
